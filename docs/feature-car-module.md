## 二、一期功能范围（MVP，去掉费用台账后）

### A. 车辆档案（多车）
- **基本**：名称/昵称、品牌、车系型号、车牌号（敏感）、车辆类型（轿车/SUV/MPV/皮卡/摩托/其他）、能源类型（燃油/纯电/插混/油电混动）、颜色
- **证照**：VIN、发动机号、注册日期、购买日期
- **状态**：当前里程（km）、状态（在用车/已出售/已报废，历史保留）
- **照片**：**多图相册**（首图为封面；支持从附件库选择多张、上传、拖拽排序、设封面、删除）
- **关联**：车主（单选人员）+ 常用驾驶人（多选人员）— 均为可选
- **其他**：备注、前台展示开关（默认关）、重要开关（默认开，参与提醒）、拖拽排序

### B. 到期提醒项（每车多项，逐项开关）
| 项 | 字段 | 默认提前天数 |
|---|---|---|
| 交强险到期 | 保险公司、保单号（敏感）、到期日 | 15 天 |
| 商业险到期 | 同上 | 15 天 |
| 年检到期 | 下次年检日期 | 30 天 |
| 保养提醒 | 上次保养日期、上次里程、间隔月数 / 间隔公里 | 14 天 / 500km |
| 车船税 | 到期日 | 15 天 |
| 自定义项 | 名称、日期、提前天数 | 7 天 |

- 每项可**单独设置提前天数**（留空用全局默认）；可**启用/停用**
- 保养支持**日期 + 里程双条件**（里程为估算，需用户更新当前里程）

### C. 前台展示
- 「爱车」视图：车辆卡片（封面图、名称、品牌型号、**脱敏车牌**）、到期事项（仅"前台展示"开启的项）
- 相册：前台默认显示封面；可在设置中允许前台浏览相册
- **永不出现**：完整车牌、VIN、发动机号、保单号、购买价格（字段级裁剪，无开关放开）

### D. 数据与管理
- 车辆列表**拖拽排序**；操作日志记录车辆增删改（`targetType=CAR`）
- 导出/导入：JSON **v3**（含车辆与相册），兼容 v1/v2 旧文件
- Finder API：`listAllCars()` / `listUpcomingCarEvents(days)`

### E. 二期候选（暂不做）
统计卡片（车龄/里程/年内到期数）、提醒历史归档、维保记录时间线、多车对比。

## 三、数据模型草案

```
Car (importantdates.halo.run/v1alpha1, plural: cars)
  spec:
    displayName      名称/昵称
    brand / model    品牌 / 车系型号
    plateNo          车牌号（后台可见；前台永远脱敏）
    vehicleType      类型      energyType  能源类型   color 颜色
    vin / engineNo   车架号 / 发动机号（敏感）
    registeredDate   注册日期   purchaseDate 购买日期
    mileageKm        当前里程   mileageUpdatedAt 里程更新日期
    status           IN_USE / SOLD / SCRAPPED
    photos:          [{ url, name, isCover, sortOrder }]   # 多图相册
    ownerName        车主（Person.name，可空）
    driverNames[]    常用驾驶人（Person.name 列表，可空）
    note             备注
    visible          前台展示（默认 false）
    important        参与提醒（默认 true）
    sortOrder        拖拽排序
    reminders:       [{ key, label, date, remindDays, enabled,
                        insurer, policyNo,           # 保险类
                        intervalMonths, intervalKm, lastServiceDate, lastServiceKm }]
```

配置项（插件设置新增「车辆设置」组）：全局默认提前天数、启用哪些提醒项模板、车辆照片附件分组（策略+分类，复用现有实时下拉）、前台是否展示车辆区块、是否允许前台浏览相册、**是否启用性别卡片皮肤**。

## 四、前台页面方案（单页 + 视图切换）

路由保持 `/important-dates`（兼容已有链接与主题覆盖模板），页面顶部新增**分段切换器**：

```
[ 生活 ]  [ 爱车 ]        ← 默认「生活」，切换写入 URL ?view=car（刷新/分享保持）
─────────────────────────────
顶部横幅提醒（随视图变化）
─────────────────────────────
生活视图：重要日期（全部）＋ 重要的人（卡片显示与本人相关的最近日期倒计时）
爱车视图：车辆卡片（封面、脱敏车牌、到期徽章、车主/驾驶人）＋ 到期事项列表
          ＋ 重要的人（卡片标注「车主 / 驾驶人」，仅显示与车相关的人）
```

- **人员区块两种视图都显示**（符合"人员永远显示"）；区别在于卡片上呈现的信息与语义
- 主题覆盖模板（`templates/important-dates.html`）会新增变量：`view`、`cars`、`carEvents`、`carOwners`
- 设置项：是否显示切换器、默认视图、各视图显示哪些区块

## 五、性别卡片皮肤（我的想法）

关联人员（车主/驾驶人）后，让车辆卡片有性格：

| 场景 | 皮肤 | 设计方向 |
|---|---|---|
| 车主性别 = 男 | **酷（Cool）** | 深灰/碳纤维纹理底、冷色高光（蓝/银）、直角硬朗、速度线元素、轮胎/齿轮图标 |
| 车主性别 = 女 | **可爱（Cute）** | 奶油/粉彩底、更大圆角、贴纸与爱心/星星点缀、柔和渐变、圆润图标 |
| 未关联 / 性别未填 / 保密 | **中性（Neutral）** | 现有卡片风格（与日期/人员卡统一） |

实现要点（零成本、零资源）：
- 纯 CSS 变量 + 类名（`car-skin-cool` / `car-skin-cute` / 默认），不引入外部图片
- 作用范围：车辆卡片（前台默认应用；后台可选，默认也应用，方便站主自己看着开心）
- 设置里提供**总开关**（默认开），可关闭回到中性风格
- 驾驶人多人时：以**车主性别**为准；无车主则取第一位驾驶人

> 如果你有更具体的偏好（例如按能源类型分色：电车=环保绿、燃油=机械橙），可以叠加，告诉我即可。

## 六、提醒渠道方案（建议，待你确认）

**推荐：一套事件管线 + 分渠道开关**，避免"车辆一套、日期一套"造成维护与噪音问题。

1. **统一计算**：日期事件 + 车辆到期事件进同一列表，按"还剩 N 天"排序（同级时日期事件优先，可配置）
2. **分渠道开关**（设置项）：
   | 渠道 | 默认 | 说明 |
   |---|---|---|
   | 控制台仪表盘小组件 | 开启 | 合并展示，带图标区分（📅 / 🚗），可按类型分组 |
   | 后台横幅 | 开启 | 合并展示 |
   | 前台横幅 | 开启 | **仅显示"前台展示"开启**的日期与车辆事项 |
   | 全站悬浮弹窗 | 开启 | 可设置优先级与条数 |
3. **降噪规则**（解决"多车多事项弹窗太多"）：
   - 每个类型最多显示 N 条（默认 2，可配 1–5）
   - 超出时**合并为一条汇总**："「交强险」明天到期，另有 2 项 7 天内到期"
   - 类型优先级：按紧急度（默认）/ 日期优先 / 车辆优先
4. **文案**：沿用现有风格 —— "「交强险」还有 7 天就到啦～"，车辆事项前可加车型昵称："「小白」的交强险还有 7 天就到啦～"

> 如果你更希望"车辆提醒单独一套样式/单独入口"，也可以做，但会多一套配置与文案维护。

## 七、命名方案（候选）

| 候选 | 优点 | 缺点 |
|---|---|---|
| **记得** | 简洁好记、有情感（记得每个重要日子） | 检索性弱，需靠副标题补关键词 |
| **重要日子与爱车** | 一眼看懂、搜索友好 | 稍长 |
| **生活册 / 生活记事** | 覆盖日期+人+车、中性 | 略平淡 |
| **日子** | 极简 | 太泛 |
| **念念** | 文艺、"念"=纪念/挂念 | 检索性弱 |

**我的建议**：显示名用 **「记得」**（或「念念」），**副标题/简介固定带关键词**：
> 记得 · 重要日期与爱车 —— 纪念日、生日提醒 · 家人档案 · 车辆保险年检保养

理由：商店检索主要靠简介与 README 关键词命中，显示名可以更简洁有辨识度；若你更看重"一眼看懂"，就用 **「重要日子与爱车」**。

**技术约束（重要）**：只改**显示名（displayName）**，**绝不能改插件 ID（plugin name = `plugin-important-dates`）**——ID 变了等于新插件：数据不兼容、菜单/路由/设置全部重建、用户需重装。

### 改名对应用市场的影响（你问的问题）
- 商店以**应用 ID** 为主键，displayName / 简介 / README / 截图属于**可变更的元信息**；
- 已上架应用修改元信息，通常需要**重新提交变更审核**（以平台当前规则为准），但**不需要下架重发**；
- 稳妥做法：**把改名与 1.2.0 版本提交放在同一次**——版本说明里写明"应用更名为 XX，功能不变"，一次审核完成，避免多跑一轮；
- 若平台允许直接编辑应用信息且免审，则随时可改；上线前我建议你在开发者后台确认一下"编辑应用信息是否需要审核"。
