## 修复：拖拽排序保存时的 503（反向代理限流把请求挡在了 Halo 之外）

**现象**：拖拽人员/日期/座驾卡片调序时提示「保存排序失败：Request failed with status code 503」，弹窗里是反向代理返回的 `503 Service Temporarily Unavailable`，而 **Halo 日志里没有任何记录**。

**根因分析**：

1. 旧的保存逻辑把整张表重新编号，并用 `Promise.all` **并发**提交；而每次提交走的是「先 GET 最新版本 → 再 PUT」两步。
2. 实测（4~6 个对象的列表拖一次）：**6 个 GET + 6 个 PUT，最大并发 6，全部集中在 45 毫秒内**。
3. 站点前有反向代理（nginx / CDN）。nginx 的 `limit_req`（请求速率）与 `limit_conn`（并发连接数）**默认就用 503 拒绝**，且由 nginx 自己回复——请求根本没到 Halo，所以 **Halo 日志为空**，这正是"服务端查不到报错"的原因。

**修复**：

1. **只写必要区间**：比较新旧顺序，只对真正发生位移的连续区段写入（数据若是手工改过的非 1..n 形态，则回退为整表重排，保证正确）；
2. **改用 JSON Patch**：`PATCH /persons/{name}` + `[{op:"add", path:"/spec/sortOrder", value:N}]`，只改一个字段，不再先 GET 再 PUT，**请求数直接减半**；
3. **串行提交**（间隔 40ms）：最大并发降到 **1**，不再形成突发流量；
4. **对 429/5xx 自动重试**（300/600ms 退避，共 3 次），瞬时抖动可自愈；
5. **报错更明确**：重试后仍失败时提示「站点反向代理暂时不可用（HTTP 503），请稍后再拖一次」，而不是只抛原始状态码。

**实测对比**（同一台实例、同样的拖拽操作）：

| | 修复前 | 修复后 |
|---|---|---|
| 写请求数 | 6 个 PUT（+6 个 GET） | 5 个 PATCH（0 个 GET） |
| 最大并发 | **6** | **1** |
| 请求结果 | 突发、易被代理 503 | 全部 2xx，顺序正确落库 |

> 提示：若站点反向代理的限流设置非常严格（例如 `limit_conn` 只允许极少并发），仍建议检查一次 `limit_req` / `limit_conn` 配置；本插件此次已不再产生突发请求。

## 验证（全新 Halo 2.26 实例）

- 冒烟回归 `halo-smoke.mjs` **50/50 PASS**；浏览器端到端 `browser-121-e2e.mjs` **13/13 PASS**；附件库来源范围 `verify-album-scope.mjs` **5/5 PASS**；
- **拖拽排序专项 `verify-sort-save.mjs` 6/6 PASS**：断言写入最大并发 = 1、无逐条 GET、全部 PATCH、无 5xx、排序结果正确落库。
- 顺带加固：冒烟脚本的就绪检测现在同时确认「插件接口 + 前台页面」连续两次正常，避免安装后 Halo 重启插件的窗口期被误判为失败（该窗口期前台可能瞬时 500 `Scheme not found`，属 Halo 插件生命周期，非本插件缺陷）。
